# PROJECT SAFETY RULES: MECHANICAL PRO NOTES
**Document Identifier:** DOC-MPN-005  
**Project:** Mechanical Pro Notes (Personal Reference App)  
**Classification Standard:** Strict 6-Tier Evidence Classification  
**Status:** PERMANENT BINDING POLICY - REVISED MASTER PROMPT 01-A  
**Last Updated:** 2026-11-11  

---

## 1. Absolute Directives & Safety Governance
These rules are permanent, mandatory, and inviolable. Every AI agent, engineer, or collaborator operating on Mechanical Pro Notes must strictly adhere to these protocols.

---

## 2. Rule 01: Scope Quarantine (Personal-Only Application)
1. **Personal Reference Boundary:** Mechanical Pro Notes is exclusively a personal engineering and plant maintenance reference tool for the project owner's Android smartphone.
2. **Prohibited Additions:** Under NO circumstances may the assistant introduce, propose, or allocate development effort to:
   - Google Play Store deployment, packaging, or public listing.
   - Public product marketing, branding, or launch infrastructure.
   - Advertisements, monetization SDKs, commercial billing, or subscription locks.
   - Multi-user authentication, cloud databases, or remote user access tiers.
   - Anti-piracy, DRM, or duplicate copy protection systems.

---

## 3. Rule 02: Repository Isolation & Future Target Boundary
1. **Single Authorized Target:** The ONLY authorized future remote repository is:
   ```text
   researchbangla/mechanical-pro-notes
   ```
2. **Total Ban on Unrelated Repositories:** Under NO circumstances may the assistant interact with, reference, clone, push to, or pull from external repositories—specifically including `GarmentFlow-AI-Payment-Service` or any other client repository.
3. **No Cross-Contamination:** Code, assets, or text from external repositories must never enter this workspace.

---

## 4. Rule 03: Workspace-First & Owner-Controlled GitHub Push Protocol
1. **Workspace Development First:** All development, testing, documentation, and asset preparation must occur in the Gemini Workspace.
2. **Owner-Controlled Push:** The project owner personally performs all GitHub pushes.
3. **Assistant Responsibilities:** The assistant prepares the project, verifies changes, and provides clean, exact recommended commit messages.
4. **Honesty Mandate:** The assistant must NEVER claim that a Git push or commit occurred unless it was actually executed and verified.
5. **No Credential Requests:** The assistant must never request GitHub passwords, personal access tokens (PAT), or private keys.

---

## 5. Rule 04: Zero Grok Dependencies
1. This is a clean project baseline in the Gemini Workspace.
2. There are NO Grok workspace files to recover, migrate, compare, or investigate.
3. No Grok-related forensic investigations, SHA comparisons, or historical blob reconstructions are permitted in the active roadmap.

---

## 6. Rule 05: Free-First Cost Policy
1. The project operates under an absolute **FREE-FIRST** financial policy.
2. The assistant must NEVER provision, purchase, or connect to:
   - Paid Cloud APIs (paid Gemini tiers, OpenAI, Claude, AWS, Azure, Google Cloud paid tiers).
   - Paid databases or storage servers.
   - Paid domain names or commercial hosting services.
   - Any service that requires credit card billing or monthly subscription fees.
3. All functionality must rely exclusively on local device execution (offline Room SQLite, local computation) or open-source software.

---

## 7. Rule 06: Zero Manual Technical Burden on Mobile Owner
1. The project owner operates exclusively from an Android smartphone.
2. The assistant must NEVER instruct the owner to:
   - Run complex terminal commands.
   - Manually edit source files, lines of code, or JSON/XML configs.
   - Perform technical configuration manually where automated tools exist.
3. Clear Bengali explanations and briefings must accompany all technical deliverables, while code, documentation, and filenames remain in English.

---

## 8. Rule 07: Technical Honesty & Classification Integrity
1. **Never Invent Technical Facts:** Never fabricate machine specifications, safety settings, operating limits, or statutory codes.
2. **Strict 6-Tier Classification:** All requirements, facts, and recommendations must be properly tagged:
   - `[A. VERIFIED CURRENT FACT]`
   - `[B. HISTORICAL REFERENCE]`
   - `[C. OWNER-APPROVED REQUIREMENT]`
   - `[D. PROPOSED DECISION]`
   - `[E. UNVERIFIED INFORMATION]`
   - `[F. UNKNOWN OR MISSING INFORMATION]`
3. **Unapproved Items Remain PROPOSED:** Any technical proposal (e.g. Kotlin, Compose, Room DB) without explicit owner sign-off must be labelled `[D. PROPOSED DECISION]`.

---

## 9. Rule 08: Mandatory Checkpoints & Non-Destructive Operation
1. The assistant must maintain up-to-date documentation checkpoints (`CURRENT_WORK_CHECKPOINT.md`, `PHASE_PROGRESS_TRACKER.md`, `SESSION_HANDOVER.md`).
2. File deletion, directory pruning, or resets must never be performed without prior owner review.

---

## 10. Rule 09: Mandatory STOP Conditions
The assistant MUST immediately halt execution, execute no further commands, and await Owner review when:
1. A phase deliverable or master prompt task is completed.
2. A technical proposal requires owner review and approval.
3. A GitHub repository preparation step is completed and ready for the owner's push.
4. Any ambiguity arises regarding plant equipment or safety-critical operating parameters.
